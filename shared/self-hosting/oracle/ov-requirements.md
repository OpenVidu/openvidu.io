- The [OpenVidu CLI](/docs/self-hosting/openvidu-cli.md#install-the-openvidu-cli).
- An Oracle Cloud tenancy and [**Terraform** :fontawesome-solid-external-link:{.external-link-icon}](https://developer.hashicorp.com/terraform/install){:target="_blank"} on your PATH (1.5.0 or later; 1.12.0 or later with `--remote-state`, whose `oci` backend needs it): `ov` drives your own Terraform, so the provider plugins, the state and the audit trail are the ones that apply.
- The [`oci` CLI :fontawesome-solid-external-link:{.external-link-icon}](https://docs.oracle.com/en-us/iaas/Content/API/SDKDocs/cliinstall.htm){:target="_blank"}, configured with your **OCI API key** (`~/.oci/config`), which Terraform signs in with too. `ov` reads the stack's secrets and Object Storage with it. On Elastic and High Availability, `jq` as well: the template runs `oci` and `jq` on your machine to drain the media nodes a lower count removes and, on destroy, to terminate the ones the pool left behind.
- The compartment OCID (`--oci-compartment`, otherwise `$OCI_COMPARTMENT_OCID`), which has no default. The tenancy, the user and the region default to your `oci` profile's: `--oci-tenancy` / `--oci-user` / `--oci-region` (otherwise `$OCI_TENANCY_OCID` / `$OCI_USER_OCID` / `$OCI_REGION`) only say others, and a region found nowhere is `eu-frankfurt-1`.
- Permission to create compute instances, a virtual cloud network with a subnet and network security groups, an Object Storage bucket, a Customer Secret Key and a KMS vault for the stack's secrets (plus, on Elastic and High Availability, an instance pool with its autoscaling configuration and a Functions application), and dynamic groups and policies in the tenancy. `ov` reads back what the stack publishes, so the user must also be allowed to read the stack's secrets.
- **One vault per stack.** The stack publishes its URL, credentials and access as secrets with fixed names, so a vault holds the secrets of one stack at a time. By default the template creates a vault of the stack's own; OCI deletes a vault only after a waiting period of at least 7 days. `--oci-vault <ocid>` publishes into a vault of yours instead, and the deploy warns why to avoid it: two stacks in one vault mix their secrets, every deploy adds versions to the same secrets until Oracle answers `LimitExceeded`, and a destroy leaves the stack's credentials in it.
- **One Customer Secret Key per stack.** The template mints a Customer Secret Key for the instance to reach Object Storage over its S3-compatible API. OCI caps Customer Secret Keys at **two per user**, so at most two of these stacks can run under one user at a time.

Before anything is created, in both modes, `ov stack deploy` looks for these programs and the session (`oci os ns get`, then that your profile belongs to the stack's tenancy and can read the compartment); with something missing it creates nothing, lists all of it and exits `10`. Then it reads, still creating nothing, the stack's dynamic-group and policy names (taken: exit `2`), the region's availability domains, the shapes there, the OCPUs and memory free, the vaults and your Customer Secret Keys (what does not fit: exit `10`).

You need neither a key pair nor a domain: the template generates an SSH key pair for the stack, and without `--domain-name` the stack derives an `sslip.io` name from its public address (on High Availability, from the load balancer's), so Let's Encrypt has a name to certify on Single Node and Elastic. Use your own domain for anything beyond testing.
